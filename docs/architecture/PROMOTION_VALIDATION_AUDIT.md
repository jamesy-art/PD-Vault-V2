# Promotion Validation Audit

**Date:** 2026-08-07  
**Task:** A7-R3 — Audit only (no code changes)  
**Subject:** Why `promote.js` rejects every staging Job  
**Trace package:** `wiki/jobs/_staging/nike-inc-lead-designer-tennis-apparel-color-design/`

---

## Executive verdict

Every Job fails for the **same three missing promote-path gates**, not because of broken path discovery after the `_staging` / `_ready` refactor.

Nike (and all 14 staging packages) fail with:

1. `Quality Report missing — run Quality Checker first`
2. `Resolution Report missing — run Entity Resolution first`
3. `Editorial review incomplete — set editorial_status to approved …`

Those checks are **real Track A4 / A5 / editor gates**. They are **not** obsolete validators pointing at dead locations. Generate does **not** produce the sidecar files Promotion loads. Generate also leaves `editorial_status: canonical`, which Promotion correctly refuses.

## 2. Nature of Quality / Resolution / Approval

| Gate | Real pipeline stage? | Generated by generate.js? | Artifact type | Obsolete? |
|------|----------------------|---------------------------|---------------|-----------|
| **Quality (A5)** | **Yes** — `node scripts/quality/check.js` | **No** | Sidecar files `quality-report.json` + `quality-status.json` written by `QualityChecker` | **No** |

## 3. If Quality already runs during generate — why can’t Promotion detect it?

**It does not run during generate.**

- No call from `MarkdownGenerator` / `generate.js` into `QualityChecker`.
- No write of `quality-report.json` / `quality-status.json` on generate.
- FM may contain null `editorial_quality` / `capture_quality` — Promotion ignores those keys and only accepts the A5 sidecar files.

So there is nothing for Promotion to “detect.”

---

## 4. If Entity Resolution already runs during generate — why can’t Promotion detect it?

**Full Track A4 Entity Resolution does not run during generate.**

Generate runs **Company Canonical Identity (A2-R9)** and related enrichment, which:

- Writes `company_identity` into FM / generator report  
- Does **not** write `resolution-report.json`  
- Leaves `relationships.company: null` on Nike (stub from `yamlGenerator.js`)

Promotion only accepts:

```
wiki/jobs/_staging/<slug>/resolution-report.json
```

produced by `scripts/resolution/resolve.js` → `EntityResolutionEngine` → `canonicalRelationshipWriter`.

Partial generate-time company identity ≠ A4 resolution report.

## 7. Obsolete assumptions?

| Hypothesis | Finding |
|------------|---------|
| Promotion looks for obsolete `content/jobs/canonical/…` report paths | **False** — loads sidecars beside the resolved staging markdown |
| Promotion expects obsolete `ready.md` / `canonical.md` names for gates | **False** — gates are JSON sidecars + FM |
| Quality/Resolution merged into generate, validators obsolete | **False** — A4/A5 remain separate CLIs; generate substitutes are different artifacts |
| Path drift after A7-R1 caused false negatives | **False** — files are simply not written; discovery of staging packages works (`--mode all` reached validation for every Job) |

What *is* easy to misread as “obsolete”:

- Docs / CLI help still mention legacy `--canonical-dir content/jobs/canonical/…` in places  
- Generate embeds rich company metadata that looks “resolved” but is not A4  
- First live production (Nike + Burberry) **did** run ER + Quality + approve before promote — current vault staging no longer has those sidecars (regenerated / not re-run)

## Recommended fix (guidance only — not implemented)

**Operational (implemented):** use mode CLIs — see `JOBS_GENERATE_TO_PROMOTE_WORKFLOW.md`.

```bash
node scripts/resolution/resolve.js --mode changed
node scripts/quality/check.js --mode changed
node scripts/editorial/approve.js --mode changed --actor editor:you
node scripts/ready/promote.js --mode changed
```

**Product / UX (optional later):**

1. Promote `--mode all` should print a clear “run resolve → quality → approve first” summary (already encoded in errors).  
2. Consider mode CLIs for resolve/quality mirroring promote/export (`--mode all`).  
3. Do **not** silently accept `company_identity` or `generator-report` as Quality/Resolution substitutes without an explicit architecture decision — that would weaken the Ready gate.  
4. If the product goal becomes “generate ≈ promote-ready,” that is a **pipeline redesign** (fold A4/A5 into generate or emit compatible sidecars) — out of scope for A7-R3.

## Final questions

### Why does every Job fail?

Because none of the 14 staging packages have completed the three promote gates: **A4 resolution report file**, **A5 quality report file**, and **editorial approval** metadata. Generate output alone is insufficient by design.

### Which validation is actually missing?

All three are **actually missing on disk / in FM**, not mis-detected:

1. `quality-report.json` (or eligible `quality-status.json`)  
2. `resolution-report.json`  
3. `editorial_status: approved` (or equivalent review/history)

### Which validation is obsolete?

**None of these three.** They match current A4 / A5 / Ready architecture.  
Obsolete *confusion* is treating generate-time `company_identity` / cleaner reports as substitutes for those gates.

### Should Promotion validate generated metadata instead of report files?

**Not without an explicit redesign.** Today:

- Quality is a dedicated read-only checker whose contract is the sidecar report  
- Resolution’s contract is the resolution report (+ relationship write)  
- Approval is a deliberate human/lifecycle stamp  

Accepting generate metadata instead would collapse Ready into “whatever generate wrote,” which contradicts Track separation and the certified promote gate. A future change could *emit* compatible sidecars from generate, or promote could *invoke* A4/A5 — both are design changes, not audit fixes.

### Is this a regression introduced during the pipeline refactor?

**No.** A7-R1/R2 changed Ready location and CLI modes; they did not invent these three checks. Failures match pre-existing `promotionValidator.js` behaviour. The vault simply has generate-only staging packages (no resolve/quality/approve rerun). Earlier Nike/Burberry production success required those steps manually before promote.
